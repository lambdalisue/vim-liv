# 0004 — `liv.core` (the seam)

`liv.core` is the single, minimal, invariant seam over the editor. What it
**owns** is **value marshaling** (see [0005](0005-marshaling.md)) and the
**vimscript** entry points — exposed as a small fixed set of generic primitives,
**no per-function or feature APIs** (those would force core to know every Vim
function and would bloat it; cf. denops' `Denops` interface, which is just
`call`/`dispatcher`).

## What "only core touches `vim.*`" really means

The invariant that must stay centralized is **marshaling**, not every call site.
Because `liv.std` modules select a `_vim`/`_nvim` backend once at import, a given
backend only ever runs on its own editor — so a backend reaching its *own*
editor's native API is safe and need not be funneled through a core primitive.
Concretely:

- `liv.core` is the only place that **marshals**: the conversion lives entirely
  inside `core.marshaled`/`call`/`eval`/`cmd`. Backends may *name* native function
  symbols (`vim.fn.*` on Vim, `vim.api.*` on Neovim), but only to bind them
  through `core.marshaled` — the conversion itself never leaves core.
- `liv.std` `_vim` backends bind **vimscript builtins** as marshaled references —
  `core.marshaled(vim.fn.getbufline)` — and use `core.eval`/`cmd` for
  expressions/Ex commands. `core.call` (by name) is kept for dynamic dispatch.
- `liv.std` `_nvim` backends bind the **Neovim native Lua API**
  (`vim.api.*`, `vim.uv`, …) the same way through `core.marshaled`, so marshaling
  is never hand-rolled (and so omissions are impossible).
- Calling a plain Lua function needs **no** seam — both editors run Lua; you just
  call it. The seam exists only to reach the *editor's* world (vimscript via
  `call`/`eval`/`cmd`; the Neovim native API via `core.marshaled`).

## Primitives

- `core.call(fn, ...)` — call a vimscript function **by name** (over
  `vim.call`/`vim.fn`). Both editors.
- `core.marshaled(fn)` — return a Lua callable **reference** (e.g.
  `vim.api.nvim_buf_get_lines`) wrapped with the same marshaling, so it can be
  called with plain Lua values. Editor-agnostic; used by `_nvim` backends to bind
  native APIs once. Passing the real symbol keeps editor-LSP completion and
  existence-checking. Memoized per function reference (the same `fn` yields the
  same wrapper).
- `core.eval(expr)` — evaluate a Vim expression string.
- `core.cmd(cmd)` — run an Ex command string.
- `core.to_editor(v)` / `core.from_editor(v)` — low-level marshaling converters
  (for the rare value that must cross without a call).
- (optional) `core.batch(...)` — batch multiple calls.

`call`/`marshaled`/`eval` perform **bidirectional value marshaling** internally
(see [0005](0005-marshaling.md)), so arguments and return values are plain Lua
values identical across both editors.

## Editor → Lua callbacks (no public `register`)

There is **no public callback-registration primitive**. denops needs
`dispatcher`/`dispatch` only because of its RPC boundary; liv has none — the
callback's Lua function lives in the editor's own Lua runtime.

- Both editors accept **Lua functions directly** as callbacks and keep them alive:
  - Neovim: Lua functions to `vim.uv`/autocmd/keymap, etc.
  - Vim: Lua functions/closures are **auto-converted to a Funcref** (which holds a
    Lua registry reference), so they can be passed straight to
    `job_start`/`timer_start`/etc.
- Cancellation uses the **domain id** (timer id, job, autocmd id), not a callback
  handle.
- **Only exception**: Vim's string-only contexts (`:command`/`:autocmd`/`:map`
  ex-string rhs, some `expr` options) need a *name*, not a Funcref. The relevant
  `liv.std` `_vim` backend uses an **internal** id→Lua dispatch table plus a
  bundled `liv#_dispatch(id, ...)` vimscript helper. This is an implementation
  detail of those backends, **not** part of `liv.core`'s public API.

## Other core responsibilities

- `core.is_nvim` — one boolean; used by `liv.std` to pick a backend once at import.
- **require bootstrap**: Vim does not auto-wire `runtimepath` into `package.path`,
  so core installs a custom searcher to resolve bundled/dev modules. Same behavior
  on both editors.
- **Marshaling API** (see [0005](0005-marshaling.md)): `core.NIL`, `core.list`,
  `core.dict`, `core.empty_dict`, `core.is_list`, `core.is_dict`, plus
  `core.to_editor` / `core.from_editor` and the `core.marshaled` wrapper.

## Invariants

- Same code path on both editors; **no feature branching** in core (branching, if
  any, lives in `liv.std` backend selection, or is a marshaling implementation
  detail).
- Inputs and outputs are normalized to identical plain Lua values on both editors
  — this is what makes core "the same contract everywhere".
- core is the **only marshaler** and the only **vimscript** touchpoint; future
  changes to `vim.call`/`vim.eval`/`vim.command` or the marshaling rules are
  absorbed here. Neovim-native API calls live in `liv.std` `_nvim` backends (which
  only run on Neovim), always via `core.marshaled`.
