# 0006 — `liv.std` (the editor-dependent API surface)

liv's own, owned, cross-editor API (P1, P2). **`liv.std` holds only
editor-dependent modules**: each selects a backend once at import (`_nvim` /
`_vim`; see [0003](0003-architecture.md)) and touches the editor only via
`liv.core`. Purely computational modules do **not** live here — they live in the
editor-independent `liv.lua` namespace (e.g. `liv.lua.path`, `liv.lua.async`; see
the placement rule in [0003](0003-architecture.md)).

Modules are **named by purpose**, not by which pure engine they happen to use:
e.g. external-process execution is `liv.std.process`, not a same-named
re-export of `liv.lua.async`. Where an editor-dependent module needs async
composition, it wires editor leaves (schedule/system) into the pure
`liv.lua.async` engine ([0007](0007-async.md)).

## Conventions (normative; apply to all modules)

- Ranges **1-based, inclusive**. Handles are integer ids; `0`/`nil` = current.
  Positions `{line, col}` 1-based. Failures `error()`. Callbacks are plain Lua
  functions. Names are distinct from Neovim (P2).

Naming intent: module names follow denops/std (`variable`, `function`,
`mapping`, `popup`) so the cross-editor surface reads like the familiar
denops vocabulary rather than either editor's native API. `buffer.lines`/
`buffer.wipe` stay distinct from `nvim_buf_get_lines`/`delete` (1-based
inclusive); `mark` is the decoration domain word (≠ extmark). `autocmd`
keeps the shared domain word —
`:autocmd` is an Ex command on both editors, so it is editor-vocabulary, not a
Neovim coinage; a distinct name (e.g. `event`) only obscures what it is.

### Why `json` and `fs` are here (not in `liv.lua`)

Both look partly pure, but each is correctly editor-dependent — and each backend
**must carry a note explaining the choice** (see the placement rule in
[0003](0003-architecture.md)):

- **`json`** — encode/decode *could* be pure Lua, but a correct, fast JSON
  (number formatting, escaping, `NIL`/empty-container handling consistent with
  marshaling) is heavy and error-prone to reimplement, while both editors ship a
  solid native one. So `liv.std.json` wraps `vim.json` (Neovim) / `json_encode` /
  `json_decode` (Vim) rather than reimplementing it in `liv.lua`.
- **`fs`** — `read`/`write` alone could use stock `io.*`, but the full contract
  needs the editor: `stat` and `scandir` have no stock-Lua equivalent (LFS is a C
  module, out of scope) and true async needs `vim.uv`. A library author who only
  needs read/write can use stock `io.*` directly, so no pure `liv.lua.fs` split.
- **`hash`** — `sha256` is editor-dependent because both editors ship a native
  `sha256()` builtin (a C implementation), so `liv.std.hash.sha256` routes through
  it as the fast path rather than running the pure-Lua block loop. Because that
  builtin is identical on both editors (same lowercase hex), this is a single
  module with **no backend split** (the `text`/`sign`/`function` precedent, not
  the observable-diff `json` split). The portable digests themselves
  (`md5`/`sha1`/`sha256`, plus `hmac`) live editor-independently in the pure
  `liv.lua.hash` (along with `liv.lua.base64`), L1-testable against published
  vectors; `liv.std.hash.md5`/`sha1` delegate to it because the editors do not
  both guarantee those as builtins.

### Why `bufname` is here (a pure exception)

`bufname` is genuinely pure (no editor, no backend) and by the placement rule
([0003](0003-architecture.md)) a pure module belongs in `liv.lua`. It lives in
`liv.std` as a deliberate exception for two reasons, both about coherence rather
than editor-dependence: (1) it mirrors **denops/std `bufname`**, keeping the
cross-editor surface aligned with that familiar vocabulary; and (2) it is the
naming convention for editor **buffer names**, used directly alongside the
editor-dependent `liv.std.buffer`. Because it has no editor requirement it also
has **no backend and no `liv.std.has` gate** — `init.lua` is a plain re-export of the
pure impl, and the module carries this same rationale as a placement note.
(Generic RFC 3986 URI work — `parse`/`build`/`encode`/`decode`/`encode_query`/
`decode_query` — lives in the pure `liv.lua.uri` module, not here; `bufname` is a
buffer-name codec, not a general URI codec.)

### Why `text` is split (pure algorithms + editor leaf)

`liv.std.text` is editor-dependent only in one spot: measuring display columns
needs a builtin (`strdisplaywidth()`), because Lua's `#str` counts bytes, not
terminal columns. So the **algorithms** — `truncate` / `pad` / `align` / `wrap`
plus a UTF-8 code-point iterator (`chars`) — live pure and editor-independent in
`liv.lua.text`, each taking an injected `width_fn(s) -> integer`; they are
deterministic and L1-testable with a fake width function. `liv.std.text` is just
those algorithms wired to the editor's real width
(`core.marshaled(vim.fn.strdisplaywidth)`). Because `strdisplaywidth` behaves
identically on both editors
and is the pinned cross-editor display-width primitive, `liv.std.text` is a single
module with no backend split (like `sign` / `function`); Neovim's `nvim_strwidth`
is deliberately **not** substituted (it diverges on tabs / `'ambiwidth'`, which
would break parity). All slicing lands on UTF-8 code-point boundaries, and the
truncate ellipsis's own width is counted so the result never exceeds the budget.

## Backends

- **Neovim backend** (`_nvim`) calls the **Neovim native Lua API** directly (it
  only runs on Neovim), binding each function once with `core.marshaled` so calls
  use plain Lua values and marshaling can't be forgotten — e.g.
  `local get_lines = core.marshaled(vim.api.nvim_buf_get_lines)`.
- **Vim backend** (`_vim`) binds **vimscript builtins as marshaled references**
  the same way — `local getbufline = core.marshaled(vim.fn.getbufline)` (e.g.
  `buffer.lines` → `getbufline`, with index adjustment) — so both backends share
  one shape and marshaling can never be forgotten. `core.eval`/`cmd` handle
  expressions/Ex commands, and `core.call` (by name) is kept for dynamic dispatch
  (the Vim 9 callback registry). A Vim 9 script companion (`.vim`, bundled,
  declared in a dependency manifest) is used only as a hot-path optimization.
- Each backend is a factory `function(core) return {...} end`; `init.lua` calls
  it with the real core. Because both backends bind native references
  (`vim.fn.*` / `vim.api.*`) they need a live editor, so backend behavior is
  verified at **L3** on both editors — not via a mock core.

## Capability and graceful degradation

- `liv.std.has(feature)` reports availability. In-contract base features work on both
  editors; power features degrade or are gated, never failing silently.
- Examples: `mark.place{virt_text=...}` — Neovim extmark virt_text / Vim
  text-property (`text`, Vim 9.0+); gated by `has("mark.virt_text")`.
  `mark.range{...,hl}` — intra-line column-range highlight via Neovim extmark
  `end_col` / Vim text-property `end_col`; gated by `has("mark.range")`.
  `popup.open{border=...}` — gated by `has("popup.border")`.
- `sign` is the opposite of a power feature: both editors have a mature sign
  column, so the base contract (text / text_hl / line_hl) works on both; only
  differential extras (per-placement priority, `num_hl`) are gated
  (`has("sign.num_hl")`).
- `fetch` — HTTPS needs an external `curl`→`wget`; with neither present
  `has("fetch")` is false (degrade, never crash). Request options map to the
  underlying tool's flags; curl is preferred and fully featured. With only wget
  present the request degrades (plain GET, empty `headers`) and `http_version` is
  ignored. Multipart `form` upload needs curl, so it is gated by
  `has("fetch.form")` — on a wget-only host `fetch(url,{form=...})` raises.
- `image` — raster display is new on both editors (Vim `+image` / Neovim
  experimental `vim.ui.img`); gated by `has("image")` (and `has("image.gui")`
  for the GUI path).

## Out of contract

treesitter, lsp, true libuv — not in `liv.std`. Authors branch via `liv.std.has` and
handle Neovim-only paths themselves. `fetch` and `image` *are* in the catalog but
are **gated power features** (external binary / brand-new and partly
experimental), not part of the always-works base contract.
