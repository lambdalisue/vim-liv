# 0006 — `liv.std` (the editor-dependent API surface)

liv's own, owned, cross-editor API (P1, P2). **`liv.std` holds only
editor-dependent modules**: each selects a backend once at import (`_nvim` /
`_vim`; see [0003](0003-architecture.md)) and touches the editor only via
`liv.core`. Purely computational modules do **not** live here — they live in the
editor-independent `liv.lua` namespace (e.g. `liv.lua.path`, `liv.lua.async`; see
the placement rule in [0003](0003-architecture.md)).

Modules are **named by purpose**, not by which pure engine they happen to use:
e.g. external-process execution is `liv.std.process`, not a same-named
re-export of `liv.lua.async`. Where an editor-dependent module needs async
composition, it wires editor leaves (schedule/system) into the pure
`liv.lua.async` engine ([0007](0007-async.md)).

## Conventions (normative; apply to all modules)

- Ranges **1-based, inclusive**. Handles are integer ids; `0`/`nil` = current.
  Positions `{line, col}` 1-based. Failures `error()`. Callbacks are plain Lua
  functions. Names are distinct from Neovim (P2).

Naming intent (avoid lookalikes): `buffer.lines`/`buffer.wipe` (≠
`nvim_buf_get_lines`/`delete`; 1-based inclusive); `event` (≠ autocmd); `map`
(≠ keymap.set); `float` (≠ floatwin/popup); `mark` (≠ extmark).

### Why `json` and `fs` are here (not in `liv.lua`)

Both look partly pure, but each is correctly editor-dependent — and each backend
**must carry a note explaining the choice** (see the placement rule in
[0003](0003-architecture.md)):

- **`json`** — encode/decode *could* be pure Lua, but a correct, fast JSON
  (number formatting, escaping, `NIL`/empty-container handling consistent with
  marshaling) is heavy and error-prone to reimplement, while both editors ship a
  solid native one. So `liv.std.json` wraps `vim.json` (Neovim) / `json_encode` /
  `json_decode` (Vim) rather than reimplementing it in `liv.lua`.
- **`fs`** — `read`/`write` alone could use stock `io.*`, but the full contract
  needs the editor: `stat` and `scandir` have no stock-Lua equivalent (LFS is a C
  module, out of scope) and true async needs `vim.uv`. A library author who only
  needs read/write can use stock `io.*` directly, so no pure `liv.lua.fs` split.

## Backends

- **Neovim backend** (`_nvim`) calls the **Neovim native Lua API** directly (it
  only runs on Neovim), binding each function once with `core.marshaled` so calls
  use plain Lua values and marshaling can't be forgotten — e.g.
  `local get_lines = core.marshaled(vim.api.nvim_buf_get_lines)`.
- **Vim backend** (`_vim`) binds **vimscript builtins as marshaled references**
  the same way — `local getbufline = core.marshaled(vim.fn.getbufline)` (e.g.
  `buffer.lines` → `getbufline`, with index adjustment) — so both backends share
  one shape and marshaling can never be forgotten. `core.eval`/`cmd` handle
  expressions/Ex commands, and `core.call` (by name) is kept for dynamic dispatch
  (the Vim 9 callback registry). A Vim 9 script companion (`.vim`, bundled,
  declared in a dependency manifest) is used only as a hot-path optimization.
- Each backend is a factory `function(core) return {...} end`; `init.lua` calls
  it with the real core. Because both backends bind native references
  (`vim.fn.*` / `vim.api.*`) they need a live editor, so backend behavior is
  verified at **L3** on both editors — not via a mock core.

## Capability and graceful degradation

- `liv.has(feature)` reports availability. In-contract base features work on both
  editors; power features degrade or are gated, never failing silently.
- Examples: `mark.place{virt_text=...}` — Neovim extmark virt_text / Vim
  text-property (`text`, Vim 9.0+); gated by `has("mark.virt_text")`.
  `float.open{border=...}` — gated by `has("float.border")`.
- `sign` is the opposite of a power feature: both editors have a mature sign
  column, so the base contract (text / text_hl / line_hl) works on both; only
  differential extras (per-placement priority, `num_hl`) are gated
  (`has("sign.num_hl")`).
- `fetch` — HTTPS needs an external `curl`→`wget`; with neither present
  `has("fetch")` is false (degrade, never crash).
- `image` — raster display is new on both editors (Vim `+image` / Neovim
  experimental `vim.ui.img`); gated by `has("image")` (and `has("image.gui")`
  for the GUI path).

## Out of contract

treesitter, lsp, true libuv — not in `liv.std`. Authors branch via `liv.has` and
handle Neovim-only paths themselves. `fetch` and `image` *are* in the catalog but
are **gated power features** (external binary / brand-new and partly
experimental), not part of the always-works base contract.
